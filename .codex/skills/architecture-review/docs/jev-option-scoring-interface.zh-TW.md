# Jev 架構選項評分介面

狀態：草稿 v0.1  
範圍：定義介面契約。本機評分器已實作於 `.local-trials/jev-api/jev_architecture_scorer.py`，由架構審查工作流在符合資格與資料政策時自動呼叫。

## 1. 目的

當架構審查有至少兩個具備證據且可行的選項時，將 Jev 作為輔助評估者，依照同一組已確認需求與限制，評估每個選項的符合程度。本機審查仍負責檢查專案、整理證據、說明理由並提出最終建議。

這個介面支援架構審查提問格式，不取代架構影響分數、使用者決策、程式碼審查或測試。

## 2. 分開呈現的訊號

以下數值必須分開呈現：

- **架構影響分數（0–10）：** 本機審查分數，用來決定 grill 深度。
- **選項符合度分數（0–4）：** Jev 依共同評分規準，對單一選項給出的機率加權期望分數；可能是小數。
- **Jev 信心（0–1）：** Jev 對該評分的信心。這不是該選項正確、安全或已核准的機率。
- **本機理由與未知事項：** 根據已檢查的專案證據，由本機審查整理；不得說成是 Jev 提供的理由。

不可把這些數值合併為單一分數，也不可將它們當成自動核准條件。

## 3. 評分資格與隱私

只有符合下列條件才呼叫評分：

- 有 2–3 個具體、互斥、有證據支持且可行的選項。
- 每個選項都以相同的使用者成果與已確認限制進行描述。
- 本機審查者已檢查每個選項是否違反已確認的硬性限制。已確認違規屬於本機否決，不可當成可行選項送交 Jev 評分；尚未釐清的檢查結果保留為未知。
- 專案資料政策允許將這類請求送往外部評估。
- 請求內容已完成去識別化與敏感資料清理。

少於兩個可比較的可行選項，或背景不足以公平比較時，回傳 **ineligible**。資料政策不允許外部評估時，回傳 **blocked_by_policy**。

只傳送精簡摘要與不透明的證據 ID。不可傳送原始碼、原始 diff、完整檔案內容、密鑰、憑證、客戶資料或完整對話。證據 ID 與本機檔案路徑、符號、測試之間的對照必須留在本機。

## 4. 本機請求契約

協定識別碼：**architecture-option-score.v1**

必要欄位：

| 欄位 | 意義 |
|---|---|
| protocol | 必須是上述協定識別碼。 |
| review_id | 本機不透明識別碼，用於關聯本次評估。 |
| question | 本次要評估的未決架構問題。 |
| outcome | 使用者可觀察到的預期成果，以及明確的範圍界線。 |
| constraints | 已確認限制；每筆包含穩定 ID、描述，以及 hard 或 soft 強度。 |
| facts | 有證據支持且已清理的架構事實；每筆包含穩定 ID，以及 verified 或 inferred 證據狀態。 |
| unknowns | 尚未確認且重要的事實或假設；每筆包含穩定 ID。 |
| options | 2–3 個候選方向；每筆包含穩定 ID、標籤、精簡方案、取捨、本機硬性限制檢查（通過或未知），以及相關事實／限制／未知事項 ID。 |
| data_policy.external_evaluation_allowed | 適用專案資料政策的授權布林值。呼叫 Jev 前必須為 true。 |
| data_policy.sanitized | 本機呼叫端確認請求已完成清理的布林值。呼叫 Jev 前必須為 true。 |

ID 必須符合以下格式：^[a-z0-9][a-z0-9_-]{0,31}$，並在單次請求內保持穩定且唯一。選項 ID 不得重複。證據 ID 可指向本機紀錄，但不可送出對應的本機路徑。

本機呼叫端必須先檢查相關程式碼、契約、呼叫點與測試。Jev 只評估已提供的事實；它不能取代專案搜尋，也不可被要求憑空推測專案事實。

## 5. Jev API 對應方式

透過現有通用 Jev client 呼叫 TypeSafe 的 POST /v1/systemone。評分 adapter 應與任務路由 adapter 分開。

- 將清理後的成果、問題、限制、事實、未知事項與選項摘要放入 state。
- 在 questions 中為每個選項建立一個具名的 score 類型問題。選項 ID 與問題名稱之間使用本機決定性的對照。
- 每個選項都使用完全相同且依序排列的 0–4 criteria 評分規準。
- 每個問題的 instructions 都要要求 Jev 僅根據提供的成果、限制、事實與評分規準評估指定選項；不可虛構專案事實或選出勝出者；若仍有重要假設未解，應反映在評分與信心中。
- model 由既有設定或明確核准的別名選擇，不要將模型名稱寫死在協定中。
- 將整組選項放在同一個批次請求，確保每個選項收到相同背景與評分規準。

評分規準，由低至高：

| 級距 | 評分指引 |
|---:|---|
| 0 | 違反已確認的硬性要求或已宣告的架構規則。 |
| 1 | 未符合核心要求，或需要重大變通方式。 |
| 2 | 部分符合需求；仍有重要缺口、假設或取捨未解決。 |
| 3 | 符合核心需求，且只有可管理、已明確說明的取捨。 |
| 4 | 高度符合已確認需求；在語意相符時重用既有能力、遵守已宣告邊界，並避免不必要的結構。 |

每個選項都依這套規準獨立評分，不為推測中的未來需求加分。4 分代表高度符合需求，不代表已證明這是唯一最佳選項。

TypeSafe 的 score 問題以有順序的 criteria 陣列表示，各位置分別對應從 0 開始的整數級距。評分答案包含 score、confidence、probabilities、legend 和 type；回應另包含 model 與 token usage。score 是期望分數，不是模型選出的整數級距。

## 6. 正規化結果契約

必要的頂層欄位：

| 欄位 | 意義 |
|---|---|
| protocol | architecture-option-score.v1。 |
| status | scored、ineligible、blocked_by_policy、unavailable 或 invalid_response 之一。 |
| review_id | 對應的本機請求 ID。 |
| model | 有取得時填回傳的模型名稱，否則為 null。 |
| usage | 有取得時填輸入／輸出 token 數，否則為 null。 |
| evaluations | status 為 scored 時，每個送出的選項各有一筆結果；其他狀態一律為空陣列。 |
| reason | 非 scored 狀態的簡短本機說明。 |

每筆選項評估包含：

- option_id
- fit_score：介於 0–4（含端點）的有限數值；保留小數精度。
- confidence：介於 0–1（含端點）的有限數值。
- probabilities：以五個評分級距（0 到 4）為鍵的機率。
- legend：保留回傳的級距描述供稽核，並檢查它與送出的評分規準相符。

Adapter 必須將答案名稱映射回原始選項 ID。面向使用者的審查結果不得暴露原始請求或回應 payload。

## 7. 驗證與失敗處理

遇到以下任一情形，回傳 invalid_response：缺少選項評分、選項重複、答案類型錯誤、分數或信心超出允許範圍、機率鍵未完整涵蓋 0–4、機率不是有限數值或超出範圍、機率總和不符合驗證規則，或級距說明與送出的規準不相符。v1 規定機率總和與 1 的差距不得超過 0.02；期望分數與回傳機率分布加權平均的差距不得超過 0.10。這些是本機 adapter 的容許差，不是 TypeSafe 的保證。

只收到部分選項的評分不能用來比較：清空 evaluations 並回傳 invalid_response。只有既有資料政策允許時才保留供稽核用的原始供應商數值；面向使用者的結果只呈現已驗證並正規化的數值。

缺少設定、驗證失敗、逾時、速率限制、供應商或網路錯誤，回傳 unavailable。不可悄悄以路由信心、捏造數值或本機猜測取代 Jev 分數。v1 僅發出一次有界請求，不自動重試。

只記錄協定版本、模型、狀態與 token 用量。不可記錄憑證、完整背景或原始 payload。

## 8. 呈現規則

每個選項分別顯示 Jev 符合度分數、Jev 信心及各級距機率分布。本機理由應附上證據參照，並將重要未知事項列在旁邊，清楚標示為本機分析。

不可把 Jev 信心描述成設計正確的機率。不可只因符合度分數較高就標成建議選項。若 Jev 訊號與程式庫證據或使用者限制衝突，應呈現差異並詢問相關架構問題。

v1 不定義信心分級、分數門檻或自動選出勝出方案；這些需要先校準，再於後續工作流設計中決定。

## 9. 介面範例

本機正規化請求形狀（示意；只含摘要）：

- protocol：architecture-option-score.v1
- review_id：本機不透明 ID
- question、outcome
- constraints：穩定 ID、描述、硬性／一般強度
- facts：穩定 ID、清理後摘要、已驗證／推論狀態
- unknowns：穩定 ID 與精簡描述
- options：2–3 個穩定 ID、標籤、方案、取捨、本機硬性限制檢查與證據參照
- data_policy：允許外部評估與已完成清理都必須為 true

正規化評分結果形狀（示意）：

- protocol：architecture-option-score.v1
- status：scored
- review_id
- model、usage
- evaluations：選項 ID、符合度分數、信心、0–4 機率與評分規準

以上是 adapter 層的正規化資料形狀；API wire format 仍依 TypeSafe schema 為準。

# 架構變更結果審查條件

狀態：草稿 v0.1  
範圍：定義如何在實作前建立本次變更專屬的審查條件，以及實作後如何依這些條件審查交付結果。本文件是審查契約，不是實作或 CI 設定。

## 1. 審查目的

結果審查要回答：**交付的變更是否實現約定成果、重用了正確能力、維持已宣告的邊界與契約，並提供足夠證據供驗收？**

在實作後、架構審查結案前使用。只執行適用的檢查，但每個不適用項目都要記錄原因。架構影響分數、Jev 分數、建置成功或作者自述，都不能取代審查證據。

## 2. 必要審查資料

審查者需要：

- 審查 ID 與受審查的 commit／diff 或明確變更檔案清單。
- 已核准的預期成果、明確不包含範圍、限制與驗收條件。
- 實作前建立並凍結的本次變更專屬審查條件基線，包含版本與適用性判斷。
- 架構影響分數、審查深度與強制升級條件。
- 決策基準；若是不需 grill 的路徑，則提供已記錄的實作邊界與假設。
- 受影響模組、責任歸屬、允許的依賴變更、契約、呼叫端／提供端及可重用候選。
- 必要驗證清單，以及可取得的結果／紀錄參照。
- 已知風險、例外與未執行的檢查。

若找不到決策基準或無法確認受審查的變更，結果應為 **BLOCKED（受阻）**，並要求補齊證據。不可在看到實作後才自行推定驗收條件。

## 3. 實作前的審查條件基線

本文件的一般條件是審查規準，不能取代針對本次變更訂定的條件。需求與架構決策明確後，必須在開始實作前，將適用條件具體化。

每項範圍內需求或重大決策都要定義：

| 基線欄位 | 必要內容 |
|---|---|
| 條件 ID | 穩定識別碼，例如 AC-01、REUSE-01、CONTRACT-01 或 ARCH-01。 |
| 來源 | 此條件要驗證的需求、限制、架構決策、風險或不包含事項。 |
| 適用性 | 標示適用，或附理由標為豁免。不可默默略過 R1–R8 任一面向。 |
| 通過／失敗條件 | 可觀察的結果或不變條件，明確指出如何判定通過或失敗。避免只寫乾淨、良好、可運作等沒有觀察定義的詞。 |
| 證據方式 | 指定測試、契約 diff、架構檢查、符號／呼叫點檢查、人工情境或其他可審查證據。 |
| 負責人 | 負責產生或審查該證據的人員／角色。 |
| 失敗處置 | 失敗是否阻擋驗收，以及需要的修正或決策。 |

開始實作前，只有符合以下條件，審查基線才算就緒：

- 每項範圍內的使用者成果與重大架構決策，都對應到一個以上的穩定條件 ID。
- 每個適用的 R1–R8 面向都已定義具體通過條件與證據方式；每個豁免都有理由。
- 必要測試／檢查已依變更風險等級列出，不能默默延後必要檢查。
- 沒有可能改變行為、責任、契約、依賴方向、遷移／生命週期或驗證範圍的未解歧義。
- 若條件涉及產品行為、品質門檻或風險承擔，使用者或指定負責人已看過並確認。

審查條件基線使用以下狀態之一：

- **READY_FOR_IMPLEMENTATION**：條件可觀察、證據與負責人已確定，重大決策也已解決。
- **NEEDS_CLARIFICATION**：條件涉及尚未解決的產品／架構選擇，或目前無法客觀描述；返回 grill 或詢問負責人。
- **BLOCKED**：缺少必要專案背景、存取權、依賴資訊或證據；不可宣稱已準備就緒。

此基線狀態判斷的是實作前是否就緒，與實作後的整體審查結果（PASS／FAIL／BLOCKED）分開記錄。

實作前凍結並標記基線版本。若範圍或需求改變，建立新版並記錄原因。不可看到失敗結果後，才降低條件來取得 PASS。

基線範例：

| ID | 通過條件 | 證據 |
|---|---|---|
| AC-01 | 請求缺少必要欄位時，回傳已宣告的驗證錯誤。 | 契約測試與已審查的錯誤 schema。 |
| REUSE-01 | 呼叫既有能力，或記錄足以支持分開實作的語意／生命週期差異。 | 候選符號、呼叫點、測試搜尋與 diff 審查。 |
| ARCH-01 | 新增呼叫遵循核准的依賴方向，且不引入禁止的循環依賴。 | 架構檢查或有紀錄的依賴檢查。 |

每次變更可複製使用的條件範本：

- 審查 ID／基線版本：
- 條件 ID：
- 來源需求或架構決策：
- 適用性／豁免理由：
- 可觀察的通過條件：
- 失敗條件與處置：
- 必要證據／檢查及負責人：
- 條件涉及產品或風險決策時，使用者／負責人確認：

## 4. 單項狀態與整體結論

每個適用條件都要有一個狀態：

| 狀態 | 意義 |
|---|---|
| PASS（通過） | 條件已滿足，且有可追溯的證據。 |
| FAIL（失敗） | 證據顯示變更違反條件或已核准的決策。 |
| NOT_RUN（未執行） | 必要命令、測試、專業審查或檢查尚未執行。 |
| BLOCKED（受阻） | 缺少必要背景、存取權或證據，無法判斷。 |
| EXEMPTED（豁免） | 此條件確實不適用；必須記錄原因並由審查者確認豁免。 |

整體結論：

- **PASS**：所有必要條件皆為 PASS，或經確認為 EXEMPTED，且沒有未解決的阻擋事項。
- **FAIL**：任何條件失敗，或實作違反已核准成果、架構決策或必要驗收條件。
- **BLOCKED**：目前沒有已知 FAIL，但必要條件為 NOT_RUN／BLOCKED，或缺少證據。BLOCKED 不代表核准。
- 若已有 FAIL，即使其他項目也缺證據，整體仍為 FAIL；另外列出受阻檢查。

已接受的剩餘風險必須附負責人，且處置方式須符合專案政策。接受風險不能把已知的契約、安全、正確性或硬性限制違規改成 PASS。

## 5. 必須通過的審查條件

| ID | 條件 | PASS 證據 | FAIL 範例 |
|---|---|---|---|
| R1 範圍與成果 | Diff 符合核准範圍；每項範圍內、可觀察的驗收條件都對應到變更行為及可審查證據。 | 決策／驗收 ID → 變更符號或契約 → 測試、檢查或審查結果。 | 未記錄的範圍擴張；必要成果未實作；行為違反明確排除事項或決策。 |
| R2 責任與邊界 | 新增或修改的行為位於約定的負責模組；呼叫與匯入符合允許的依賴方向；未新增未核准的跨邊界存取或循環依賴。 | 模組責任說明、依賴／呼叫證據、架構檢查或有紀錄的人工檢查。 | 邏輯加到不相干模組；繞過提供端內部契約；違反依賴方向、循環依賴或未核准跨邊界。 |
| R3 重用與重複碼 | 重用或擴充業務語意相符的既有能力。若新增實作，須有語意、責任、錯誤、副作用或生命週期差異作為證據。 | 搜尋詞與範圍、檢查過的候選符號／呼叫點、相關測試及簡短重用判斷。 | 新增第二份實作相同能力的函式／程式區塊，卻沒有記錄重要差異；無理由保留複製貼上的程式碼。 |
| R4 契約與相容性 | 受影響的公開／共用契約符合已宣告的輸入輸出語意、錯誤、授權、副作用與版本政策；呼叫端／提供端仍相容，或遵循核准的遷移方案。 | Schema／diff 審查、契約測試或提供端／消費端證據；需要時附 API 契約審查。 | 未記錄的 schema 漂移；破壞相容性卻沒有版本／淘汰方案；授權或錯誤語意退化；缺少必要契約審查。 |
| R5 行為與驗收 | 關鍵行為有適當證據。使用者可見行為與服務契約具備明確的主要路徑，以及相關的負面、邊界、授權與失敗情境驗證。 | 通過的相關測試結果，或明確對應驗收條件、可供審查的人工檢查紀錄。 | 關鍵驗收條件沒有驗證；相關失敗／授權路徑退化；必要測試未執行卻被標為通過。 |
| R6 資料與生命週期 | 持久資料、遷移、既有呼叫端、淘汰、回復、雙軌支援與資料不變條件皆依約處理。 | 遷移／回復證據、相容方案、資料不變條件檢查，或確認持久層未受影響的豁免。 | 破壞性或不相容資料變更沒有核准的遷移／回復方案；默默破壞既有呼叫端或持久資料。 |
| R7 風險與執行行為 | 適用的安全、隱私、效能、可用性與故障要求均符合，包括相關的輸入驗證、逾時／重試／冪等和安全記錄。 | 相關安全／隱私審查、資源／故障測試、已宣告的效能預算檢查，或有證據的豁免。 | 敏感資料外洩；授權繞過；資源使用無上限；不安全重試造成重複副作用；必要風險檢查未做。 |
| R8 變更品質與可維護性 | 新抽象有當前用途與明確負責者；命名符合語意；修改遵循專案慣例；沒有混入無關或無效程式碼。 | Diff 審查、必要時的 lint／靜態分析結果、責任與使用情況證據。 | 為推測中的未來需求新增框架；留下無說明的無效／註解程式碼或無關變更；程式碼模糊責任或重複業務規則。 |

不要求每項變更都執行所有測試類型。應根據風險與受影響邊界選擇適用檢查。對外可觀察行為應有可審查或可執行的行為情境；領域規則重大時應確認責任、不變條件與強制執行位置。架構測試能證明結構邊界，不能單獨證明業務正確性。

## 6. 重用與重複碼判斷規則

依行為與領域意義搜尋候選，不只依函式名稱搜尋。檢查可能的定義、呼叫點、測試與相關契約。

| 發現 | 審查判斷 |
|---|---|
| 業務意義、責任、輸入輸出、錯誤、副作用與生命週期相同 | 重用既有能力，或在其負責模組內擴充。沒有說明的第二份實作視為 R3 失敗。 |
| 外觀相似，但語意、授權、副作用、生命週期或責任有重大差異 | 可保留分開實作；須記錄具體差異，以及為何共用抽象會誤導。 |
| 既有 helper 接近需求但缺少必要行為 | 若擴充仍屬於同一責任模組且不破壞舊呼叫端，優先擴充並驗證相容性。 |
| 搜尋不到候選 | 記錄搜尋範圍與證據。範圍有限的搜尋不能證明整個專案都不存在相似實作。 |
| 自動重複碼工具標記程式區塊 | 先檢查語意再處置。工具指標是審查線索，不能單獨證明兩項能力應共用抽象。 |

若共用會讓不相關的領域政策或生命週期互相耦合，審查者可以否決重用；但要附上證據說明。

## 7. 風險等級與檢查選擇

架構影響分數決定架構討論深度；風險等級另行評估，避免範圍看似小就掩蓋高後果。

- **高風險**：付款、授權、法規遵循、受管制資料、安全敏感或其他高後果行為。適用時，安全／隱私與故障路徑證據為必要項目。
- **多階段**：多個子系統、API、持久化／資料庫變更、使用者旅程、跨服務工作或未解領域規則。適用時，契約、生命週期與整合證據為必要項目。
- **一般**：在既有負責模組內的有限程式碼或行為變更。
- **基本**：不影響行為／契約的文件或機械式變更。

採用符合條件中較高的風險等級。確實不相關的條件可標為 EXEMPTED 並說明原因；不能因 patch 很小就降低風險等級。

## 8. 審查發現格式與嚴重度

每筆發現須包含：

- 發現 ID 與嚴重度。
- 條件 ID（R1–R8）。
- 檔案／符號／行號或契約參照。
- 觀察到的證據與預期決策／要求。
- 對使用者或系統的影響。
- 修正方式或結案所需的驗證證據。

嚴重度：

- **阻擋**：重大正確性、安全、隱私、資料完整性、硬性限制或契約失敗；驗收前必須解決。
- **重大**：架構邊界／責任違規、無理由重複能力，或未滿足必要驗收條件；驗收前必須解決。
- **輕微**：不違反必要條件的局部可維護性問題；依專案政策接受或追蹤。
- **觀察**：資訊性紀錄，不要求修正。

若程式符合專案慣例且行為／架構條件均通過，不可只因個人風格偏好列為阻擋項目。

## 9. 結果審查紀錄

依下列欄位記錄：

| 欄位 | 值 |
|---|---|
| 審查 ID／受審查版本 | |
| 成果與範圍符合度 | PASS／FAIL／BLOCKED，附證據 |
| 架構決策符合度 | PASS／FAIL／BLOCKED，附證據 |
| 整體結果 | PASS／FAIL／BLOCKED |
| 審查條件 | R1–R8 面向狀態，以及每個本次變更條件 ID、證據參照或豁免理由 |
| 發現事項 | ID、嚴重度、條件、位置、影響、結案證據 |
| 必要檢查 | PASS／FAIL／NOT_RUN／BLOCKED／EXEMPTED，附參照 |
| 剩餘風險 | 描述、負責人、處置方式 |
| 結案條件 | 尚需修正、補交證據或核准事項 |

## 10. 重新審查與結案

- FAIL 修正後，重新檢查失敗條件與周邊可能受影響的行為。
- 若實作改變已核准的邊界、契約、責任或生命週期決策，先重開架構分流與決策閘門，再接受新設計。
- 若只是維持已核准決策的行為實作問題，重跑相關必要檢查與回歸檢查即可。
- 只有整體 PASS 才能結案；否則明確保留 BLOCKED／FAIL、缺少的證據或負責修正的人。不可將受阻審查回報為已完成。

## 11. 與工作流的關係

結果審查閘門是[架構審查工作流](architecture-review-workflow.zh-TW.md)的第 10 階段。本文件定義驗收條件與審查結果狀態；工作流文件定義如何編排流程與何時等待使用者決策。

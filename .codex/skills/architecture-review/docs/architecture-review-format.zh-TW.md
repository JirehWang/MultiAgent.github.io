# 架構審查格式

狀態：草稿 v0.1

本格式用來判斷提議中的變更會造成多大的架構影響、決定需要進行多深入的設計討論，並記錄審查證據。端到端流程編排請參閱[架構審查工作流](architecture-review-workflow.zh-TW.md)。

## 審查原則

- 根據變更的實際影響分類，不只看它屬於建構、修改、新增或刪除。
- 詢問使用者前，先檢查專案、既有契約、架構文件、呼叫點與測試。
- 只針對尚未解決、且可能改變模組責任、契約、依賴方向、相容性、遷移或風險的決策進行追問。
- 將原始碼和程式碼關係圖的觀察視為「目前實作」的證據。若專案尚未定義預期架構規則，架構符合度應標為「未知」。
- 若既有能力的業務語意、副作用、錯誤行為和責任範圍相符，優先重用。若不相符，應說明為什麼需要新增實作。

## 2. 架構影響評分

每個面向評 0 至 2 分；可行時以專案證據評分。

| 面向 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 範圍與邊界 | 單一模組內的私有實作 | 同一應用程式中的多個模組 | 公開 API、服務、平台或外部系統邊界 |
| 契約與資料 | 不變更介面或資料形狀 | 變更內部介面或行為 | 變更公開 API、共用 schema、資料庫或事件契約 |
| 責任與依賴 | 責任歸屬與依賴方向明確且不變 | 擴大既有模組責任，或責任歸屬不明 | 新增共用能力、模組／服務邊界，或改變依賴方向 |
| 相容性與生命週期 | 可逆，且不影響既有呼叫端或持久資料 | 可能影響既有行為或呼叫端 | 破壞相容性、刪除共用行為，或需要資料遷移 |
| 風險與未知事項 | 影響低，且假設已確認 | 仍有重大假設，或影響程度中等 | 涉及安全、隱私、關鍵業務／資料風險，或尚有關鍵設計決策未定 |

總分：__／10

| 總分 | 審查深度 | 處理方式 |
|---:|---|---|
| 0–2 | 不需正式 grill | 檢查可重用候選與測試後，在既有邊界內進行；記錄重要假設。 |
| 3–5 | 聚焦式 grill | 只追問可能改變本次設計、且尚未釐清的問題。 |
| 6–10 | 完整架構 grill | 實作前先釐清模組責任、契約、依賴、生命週期、風險與驗收方式。 |

### 強制升級條件

不論總分多少，遇到以下變更至少進行聚焦式 grill：

- 新增、修改、版本化或移除公開契約或跨服務契約。
- 變更共用資料模型、持久化 schema 或事件格式。
- 新增服務或共用能力，或改變允許的依賴方向。
- 刪除仍有呼叫端的共用／公開函式、介面、端點、事件或資料欄位。
- 變更驗證、授權、隱私、租戶邊界或其他高影響業務規則。

若責任歸屬、相容性、遷移或回復方案尚未釐清，或變更橫跨多個各自負責的系統，應升級為完整架構 grill。

### Goldfish 角色矩陣

Goldfish 只在上述聚焦式／完整架構 grill、或使用者明確要求獨立設計審查時啟動。審查深度仍由原本總分及覆寫條件決定；以下矩陣只決定「由誰檢查哪類問題」，不另增嚴重度分數。使用者明確要求獨立審查時，最低執行聚焦 Goldfish；若使用者明確要求完整審查或影響條件要求完整 grill，則執行完整審查。每次觸發固定包含 `Zoom Out`、`Comprehension`、`Design Critic`，再依非零面向及文件條件加入最少必要角色；相同角色只啟動一次。

| 影響面向／條件 | 觸發角色 | 審查範圍與界線 |
|---|---|---|
| 所有 Goldfish 審查 | `Zoom Out`、`Comprehension`、`Design Critic` | `Zoom Out` 檢查範圍、YAGNI、簡化、資料包中可見的重用機會及設計是否停留在正確的架構層級；不宣稱已完整搜尋程式碼。`Comprehension` 檢查資料包在沒有前情對話時是否自足、易懂。`Design Critic` 壓力測試設計邏輯、假設、取捨、失敗模式及重大風險；綠地專案時依提案檢查預計邊界。都不替使用者選方案。 |
| 範圍／邊界 > 0、責任／依賴 > 0，或決策依賴現況程式行為／消費者／重用主張；且已有程式碼 | `Codebase Details` | 依原始碼查證受影響模組、呼叫端、現有 owner、依賴方向、程式行為、消費者與可重用實作。綠地專案沒有程式碼時不啟動；`Zoom Out`／`Design Critic` 仍依提案檢查設計，只有程式庫現況才能回答的事實標為 `UNKNOWN`。 |
| 契約與資料 > 0，或明確要求實作準備度審查／進入實作交接 | `Implementation Readiness` | 檢查介面／資料語意、錯誤與副作用、必要實作邊界、遷移步驟（若適用）、測試案例和驗收條件是否可直接執行。不能因為設計將來可能實作，就假設現在已進入交接。 |
| 相容性與生命週期 > 0，且已有消費者、持久資料或程式碼 | `Codebase Details`；若需具體可執行的遷移、發布、回復或交接步驟，再加 `Implementation Readiness` | 檢查向後相容、遷移、淘汰、回復與雙軌策略。破壞性變更本身至少聚焦；遷移／回復責任未定時完整 grill。 |
| 風險與未知事項 > 0 | `Design Critic`（基線角色，聚焦風險面向） | 明列假設、失敗影響、緩解措施與需由人決定的風險。若涉及安全、授權、隱私或租戶邊界，另走 `security-auditor`；涉及法規／合規則另走 `compliance-deep`。這些領域審查不可由 Goldfish 取代。 |
| 公開／跨服務 API、事件或共用 schema | 契約／資料面向非零時由 `Implementation Readiness` 檢查；需要確認現有消費者／程式碼時由 `Codebase Details` 檢查 | 確認規格有足夠契約與消費端資訊。另啟動既有 `api-contract-guardian`／API 契約治理，確認相容性與提供端／消費端影響；不可只靠 Goldfish 宣稱契約審查通過。 |
| 必須符合指定範本、必填章節或機器可讀 schema | `Structural Validator` | 只驗證格式、結構與必填欄位；不得把風格偏好當成設計缺陷。 |
| 文件清晰度是本次成果條件，或 `Comprehension` 發現會改變意義的歧義 | `Style Editor` | 只檢查影響理解的用語、指涉與一致性；不得單為潤稿啟動 Goldfish。 |

完整審查遵循 Goldfish 的有序階段：初始 `Zoom Out`、`Comprehension`、`Design Critic`（格式／文字檢查依條件加入）；只有在決策資料包依採納的 reviewer 意見修訂後，才執行中段 `Zoom Out`；最後再依矩陣條件啟動 `Implementation Readiness` 與 `Codebase Details`。中段檢查修訂後資料包及該次變更；若沒有修訂，記錄 `NOT_APPLICABLE`。`Synthesizer` 是彙整步驟，不是額外的設計判決角色。它合併重複發現，但保留有證據的分歧、`UNKNOWN` 與未解問題；不可靜默刪除 reviewer 的發現，也不可替使用者決定方案。validation tier（`standard`／`multi_stage`／`high_risk`）本身不自動增加 Goldfish 角色，仍以架構分數、覆寫條件及實際設計產物判斷。

## 3. 依操作類型判斷

| 操作 | 通常不需完整 grill | 聚焦式或完整 grill 的訊號 |
|---|---|---|
| 建構 | 一次性原型，或不涉及長期整合的獨立工具 | 長期產品、多個模組、共用資料、部署邊界或外部整合 |
| 修改 | 內部實作變更，且責任、介面、不變條件和依賴維持穩定 | 契約語意、資料責任、共用行為或依賴方向改變 |
| 新增 | 搜尋並排除可重用實作後，在既有負責模組內新增局部能力 | 新端點、共用能力、模組／服務、持久化模型或外部依賴 |
| 刪除 | 經搜尋引用處與測試，確認未使用的私有程式碼 | 共用／公開行為、仍存在的呼叫端、持久資料、遷移、淘汰期或相容性風險 |

## 4. Grill 提問與選項設計

只詢問原始碼或專案證據無法回答，且答案可能影響設計的問題。提問前，先檢視專案，將可行的設計方向整理成清楚選項。

### 以選項提問

- 每個尚未解決的決策提供 2–3 個合理且互斥的選項。選項須來自專案證據、使用者限制和實際取捨；不要為了湊數而編造選項。
- 有證據支持推薦時，把推薦選項放第一個並標註 **（建議）**。若證據無法區分優劣，應明說並保持選項不排序。
- 每個選項用一句話說明預期行為、架構影響和主要取捨，並保留自由填寫的 **其他／自行說明** 選項。
- 一次詢問一項架構決策；只有彼此緊密相關的決策才合併提問。
- 若只剩一個可行方向，說明原因，只詢問仍需使用者決定的事項。

常見決策面向包括：成果與範圍、沿用既有負責模組或新增負責模組、直接重用／擴充／另建實作、維持相容或變更契約版本、允許的依賴方向、淘汰與遷移策略、風險與品質取捨，以及驗收檢查。實際選項應依專案調整。

### Jev 信心參考

- 將第 2 節的架構影響分數，與「對某個設計選項的信心」分開。影響分數用來決定 grill 深度；選項信心只是比較設計方向的參考證據。
- 方案評分介面草稿記錄於 [jev-option-scoring-interface.zh-TW.md](jev-option-scoring-interface.zh-TW.md)，定義 0–4 的選項符合度分數、對該評分的 0–1 信心，以及各分數級距的機率分布。這些訊號必須分開呈現。
- 專用本機評分器已實作於 `.local-trials/jev-api/jev_architecture_scorer.py`，由架構審查工作流在符合條件時自動呼叫。若不符合資格、政策阻擋、無法使用或回應無效，選項評分標示為 **無法取得**。獨立的路由 adapter 信心不是設計分數；不可改稱或捏造 Jev 分數。
- Jev 不會依這份介面回傳有程式庫證據支持的理由。本機審查者應根據已檢查的證據提供理由與不確定事項，並標示為本機分析。Jev 結果只供參考，不代表設計已獲核准，也不能取代使用者選擇。

### 選項格式

**需要決定：**［尚未解決的問題］

專案證據：［檔案、符號、契約、呼叫點或測試］

- **A.［方向］（建議）**——［預期行為與取捨］。Jev 符合度：［0–4 或「無法取得」］；Jev 信心：［0–1 或「無法取得」］；本機理由：［簡述證據］。
- **B.［方向］**——［預期行為與取捨］。Jev 符合度：［0–4 或「無法取得」］；Jev 信心：［0–1 或「無法取得」］；本機理由：［簡述證據］。
- **其他／自行說明：**［自由填寫］

1. **預期成果：** 使用者可觀察到的行為必須如何改變？明確不包含哪些範圍？
2. **責任歸屬：** 哪個模組負責這項業務能力？是否已有業務語意相符的函式或服務？
3. **重用判斷：** 檢查過哪些候選函式、呼叫點和測試？若不重用，哪項語意或生命週期差異足以支持新增實作？
4. **契約：** 輸入／輸出的格式與語意、錯誤、授權、副作用及版本相容要求為何？
5. **依賴：** 哪些模組可以呼叫這項能力？提案是否新增依賴或反轉既有依賴方向？
6. **生命週期：** 既有呼叫端和持久資料會受到什麼影響？是否需要遷移、淘汰期、回復或雙軌支援？
7. **風險與品質：** 必須滿足哪些安全、隱私、效能、可用性和故障處理要求？
8. **驗收方式：** 哪些單元、整合、契約、架構和重複碼檢查能證明變更正確？

當負責模組、重用或新增的決策、受影響契約、允許的依賴變更、相容方案和可衡量的驗收檢查都已明確時，grill 即可結束。未解事項應列為假設或風險，不應默默代替使用者決定。
